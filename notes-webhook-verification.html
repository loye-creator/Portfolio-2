FIELD NOTE 01 / PAYMENTS

Verify the webhook before you trust it.

A Lagos events business was reconciling bank transfers by hand. The replacement took seven n8n nodes, and three of them exist purely so the system never believes something it has not checked.

BUILD Orisha of Lagos STACK n8n, Paystack, Sheets STATUS Working demo

Registration for their monthly events arrived through three doors at once: Selar, WhatsApp, and straight bank transfer. The first two were fine. Transfers were the problem.

The process went like this. Someone paid. Someone on the team asked them for a receipt. Someone opened the bank account to check the amount had actually landed. Someone matched it by eye. Then someone typed the name onto a list.

At fifty to a hundred registrations an event, and well above that on the big ones, that is a person doing data entry instead of running an event. It is also slow in a way that costs money: attendees sit in limbo between paying and being confirmed, and some of them message to ask whether it worked.

Why this is a verification problem, not a plumbing problem

The obvious build is: payment notification comes in, write a row, send a confirmation. That works, and it is also wrong.

A webhook endpoint is a public URL. Anyone who finds it can post anything to it. If the system writes a row for every payload it receives, then adding yourself to a paid event guest list costs nothing more than a single HTTP request with a plausible-looking body. No payment required.

This is not hypothetical paranoia. Endpoint URLs leak through browser history, shared screenshots, logs, and anyone who has ever had access to the automation. The fix is cheap, so there is no reason to skip it.

THE RULE

A payment webhook is an untrusted claim that money arrived. It becomes trustworthy only after you check it was signed by the person who holds the secret key. Until then it is a stranger telling you they paid.

How the signature works

Paystack signs every webhook it sends. It takes the exact body of the request, runs an HMAC SHA512 over it using your secret key, and puts the result in an x-paystack-signature header.

Because the secret key never leaves Paystack and your server, only those two parties can produce a valid signature for a given body. So the check is: compute the same hash yourself, and compare. Match means genuine. No match means discard.

One detail does most of the damage when people get it wrong. You must hash the raw body exactly as it arrived, byte for byte. Not the parsed object. Not a re-serialised version of the parsed object. Most automation tools helpfully parse incoming JSON for you, and that parsing quietly changes key order and whitespace, which changes the hash, which means every genuine webhook now fails verification and you conclude the signature check is broken.

It is not broken. You hashed a different string.

Where n8n got in the way

My first version did the hashing in a Code node, the way you would in any Node script:

// This does not work in n8n.
const crypto = require('crypto');
const hash = crypto
  .createHmac('sha512', secret)
  .update(rawBody)
  .digest('hex');

n8n runs Code nodes inside a sandbox, and that sandbox does not permit require of Node's built-in modules by default. The node fails. There is no amount of rewriting the JavaScript that fixes it, because the restriction is the point of the sandbox.

The answer is that n8n already ships the capability as a first-class node. The Crypto node does HMAC with a choice of algorithms, takes the value to hash and the secret as parameters, and writes the result into the item. No sandbox involved.

So the chain became: a Code node that pulls the raw body out of the request, the native Crypto node to produce the HMAC SHA512, then a second Code node that compares the result against the header value.

WORTH REMEMBERING

When a low-code tool blocks something, check whether it offers the same capability as a built-in node before you fight the sandbox. The restriction is usually deliberate, and the supported path is usually already there.

Why the If node is separate from the signature check

A verified webhook is not necessarily a successful payment. Paystack sends events for failed charges, refunds, transfers and more, all correctly signed. The signature tells you the message is genuine. The event type tells you what the message says.

Collapsing those two checks into one condition is how you end up adding someone to the guest list because their card was declined. They are separate questions and they get separate nodes.

The notification channel changed twice

The plan was a WhatsApp confirmation, since that is where this audience already lives. I built it against the Twilio sandbox, which worked, and then hit the wall every WhatsApp Business integration hits: sending templated messages to people who have not messaged you first requires an approved template and a paid tier. Twilio SMS had the same shape of problem.

For a demo that needed to prove the chain end to end before any money changed hands, that was a blocker rather than a cost. So the final link is email over SMTP, which has no approval queue and no per-message cost.

This is worth saying plainly because it comes up constantly: the messaging channel is usually the most constrained part of any automation, and it is the part people assume will be easy. Scope it first, not last.

What it actually changed

Before, five steps, every one of them requiring a person:

  1. Attendee pays by transfer
  2. Someone asks for a receipt
  3. Someone opens the bank account
  4. Someone matches the amount by eye
  5. Name typed onto the list by hand

After, three, none of them requiring a person:

  1. Attendee pays
  2. Verified row appears
  3. Confirmation email sends itself

I built this as a working demo and took it back to the client before pricing came up, confirmed end to end against a live Paystack test payment. That ordering is deliberate. A demo that runs removes the argument about whether the thing is possible, and moves the conversation straight to what it is worth.
